# Engine commands

The Engine is one file, `.eqc/bin/eqc.mjs`, that owns the state files and the tier maths. It needs Node 18+ and nothing else. It never reads your code; the agent does that and hands the Engine Verdicts.

You will rarely run these yourself. Your agent runs them while following the Prompts. They are useful for debugging: to see what the agent sees, or to check why the Compliance level is what it is.

Run every command from the repo root:

```
node .eqc/bin/eqc.mjs <command> [args]
```

The state directory is the parent of `bin/` (so `.eqc/`). Set `EQC_DIR` to point elsewhere.

All examples on this page were produced by really running the Engine against `standards/example.md` and its Index, with sample Verdicts.

## Exit codes

| Code | Meaning |
|---|---|
| 0 | OK |
| 1 | Error or validation failure (bad input, unknown key, unusable file, mismatches), or `guard` found a regression |
| 2 | No index yet (`rules.json` is missing) |

Errors are printed to stdout, not stderr.

```
$ node .eqc/bin/eqc.mjs report
No index yet — run `eqc check` in your AI agent first (it indexes the standard).
$ echo $?
2
```

## Summary

| Command | Purpose | Writes |
|---|---|---|
| `selftest` | Run the Engine's built-in assertions | nothing |
| `reset` | Delete the Index, compliance, doc-meta and baseline (start over) | removes `rules.json`, `compliance.json`, `doc-meta.md`, `baseline.json` |
| `report [--write]` | Print (or write) the Markdown report | report file with `--write` |
| `guard` | Fail (exit 1) if a protected Rule regressed or the level dropped below the baseline | nothing |
| `rank [keyword]` | List fix candidates, easiest first | nothing |
| `ids <arg>` | Resolve which Rules to audit, grouped by Tier | nothing |
| `get <ID,ID...>` | Show a Rule and its latest Verdict as JSON | nothing |
| `merge <file>` | Merge Verdicts, recompute the level and baseline, refresh the report | `compliance.json`, `baseline.json`, report |
| `chunks <ID>` | Show progress of a Plan | nothing |
| `check-ids <doc>` | Validate the Index against the Standard file | nothing |
| `milestone add '<json>'` | Append a Milestone | `milestones.json` |
| `config get <key>` | Read a value from `config.json` | nothing |

Running with no or an unknown command prints the usage line and exits 1.

## `selftest`

Runs assertions on tier maths, merging, plan parsing and `check-ids`. Use it to confirm a vendored Engine works.

```
$ node .eqc/bin/eqc.mjs selftest
selftest ok
```

## `report [--write]`

Prints the compliance report as Markdown. With `--write`, writes it to `report_path` from `config.json` and prints the path. `--write` exits 1 if `report_path` is not set. `merge` already writes the report, so `--write` is only needed to regenerate it by hand.

```
$ node .eqc/bin/eqc.mjs report
# Example Engineering Quality Standard — compliance report

Standard: Example Engineering Quality Standard v1.0
Audited: 2026-09-29
Compliance level: Bronze

| Tier | Pass | Partial | Fail | N/A | Total |
|---|---|---|---|---|---|
| Bronze | 5 | 1 | 0 | 0 | 6 |
| Silver | 4 | 0 | 2 | 0 | 6 |
| Gold | 4 | 0 | 1 | 0 | 5 |

## Fails

- **SILVER-2** — Coverage threshold enforced — No coverage threshold in jest.config.js or CI.
- **SILVER-3** — Structured logging, no stray debug prints — 41 console.log calls under src/.
- **GOLD-1** — Release automation — Releases are tagged by hand.

## Partials

- **BRONZE-6** — Dependency vulnerability audit — npm audit runs in CI but only warns.

_Generated by eqc-kit — do not edit by hand_
```

```
$ node .eqc/bin/eqc.mjs report --write
report: …/docs/eqc-report.md
```

Verdicts of `na` get an `N/A` column and an `## Not applicable` section listing each Rule with its evidence (real output after merging one `na` and one `pass`):

```
| Tier | Pass | Partial | Fail | N/A | Total |
|---|---|---|---|---|---|
| Bronze | 1 | 0 | 0 | 1 | 6 |
| Silver | 0 | 0 | 0 | 0 | 6 |
| Gold | 0 | 0 | 0 | 0 | 5 |

## Not applicable

- **BRONZE-6** — Dependency vulnerability audit — Package has zero dependencies and no lockfile, so there is nothing to audit.
```

After a partial Audit the level says how much is missing. Real output after merging one `na` and one `pass` (15 Rules unaudited, so no Tier is reached; `merge` printed `merged 2 results · level: NONE · 15 rules not audited`):

```
Compliance level: not reached — 15 rules not audited
```

When a Tier is reached but Rules above it are unaudited, an `Unaudited: N rules` line follows the level. Before any Audit, the level reads `not audited` and every count is 0. Evidence longer than 160 characters is truncated.

Once a baseline exists (see [`guard`](#guard) and [`baseline.json`](#baselinejson)), the report adds three things after the tier table:

- a `Baseline: <LEVEL> · <n> protected · guard: ok|<k> regressions` line,
- a `## Regressions` section, only when `guard` would fail,
- a `## To reach <Tier>` section listing the Rules that block the next Tier: `fail` Verdicts and unaudited Rules in that Tier and below. Partials do not block. The section is omitted at the top Tier, and for `HARD_FAIL` or `NONE` it names the lowest Tier.

A `## Not audited` section lists every Rule with no Verdict, as `- **ID** — title`. The Fails, Partials and Not applicable sections follow.

The example below shows this layout. It was written from the Engine's report code, not captured from a run, and uses the sample Verdicts above with one Silver Rule left unaudited:

```
# Example Engineering Quality Standard — compliance report

Standard: Example Engineering Quality Standard v1.0
Audited: 2026-09-29
Compliance level: Bronze
Unaudited: 1 rules

| Tier | Pass | Partial | Fail | N/A | Total |
|---|---|---|---|---|---|
| Bronze | 5 | 1 | 0 | 0 | 6 |
| Silver | 4 | 0 | 1 | 0 | 6 |
| Gold | 4 | 0 | 1 | 0 | 5 |

Baseline: BRONZE · 13 protected · guard: ok

## To reach Silver

- **SILVER-2** — Coverage threshold enforced — fail
- **SILVER-4** — Type checking in CI — not audited

## Not audited

- **SILVER-4** — Type checking in CI

## Fails

- **SILVER-2** — Coverage threshold enforced — No coverage threshold in jest.config.js or CI.
- **GOLD-1** — Release automation — Releases are tagged by hand.

## Partials

- **BRONZE-6** — Dependency vulnerability audit — npm audit runs in CI but only warns.

_Generated by eqc-kit — do not edit by hand_
```

## `guard`

Fails when the recorded Verdicts have regressed against the baseline (`.eqc/baseline.json`, see [its shape below](#baselinejson)). Run it in CI (see [ci.md](ci.md#guard-in-ci)) or before you finish a change.

It fails when either of these is true:

- a protected Rule (one that has passed at some merge) is now `fail`, `partial`, or has no Verdict. A change from `pass` to `na` is not a regression. Protected IDs that are no longer in `rules.json` are ignored.
- the Compliance level is below the baseline level.

`guard` reads recorded Verdicts only and audits nothing. Re-audit the affected Rules first (`eqc check <IDs>` or `eqc check recheck` in your agent), then merge, then run `guard`. Levels print as raw tier IDs (`BRONZE`, `HARD_FAIL`, `NONE`).

Before the first merge there is no baseline: it prints `guard: no baseline yet` and exits 0. With no Index it exits 2.

```
$ node .eqc/bin/eqc.mjs guard
guard: ok · baseline BRONZE · 13 protected rules
$ node .eqc/bin/eqc.mjs guard
guard: REGRESSION
- BRONZE-1 — CI runs on every pull request — now fail
- level HARD_FAIL below baseline BRONZE
$ echo $?
1
```

## `rank [keyword]`

Lists fix candidates, ordered by Tier (lowest first), then Effort tier, then file count, then Rule order. Candidates are the `fail` Verdicts; if there are none, the `partial` ones. `na` Verdicts are never candidates. A `keyword` filters on the Rule title and detail (case-insensitive). If nothing matches, it says so and prints the unfiltered list.

Each line is `ID — title — files · effort [⚠ blast radius]`:

```
$ node .eqc/bin/eqc.mjs rank
SILVER-2 — Coverage threshold enforced — 2 files · small effort ⚠ ci-config
SILVER-3 — Structured logging, no stray debug prints — 18 files · medium effort ⚠ large-sweep
GOLD-1 — Release automation — 2 files · small effort ⚠ ci-config, package-install
```

```
$ node .eqc/bin/eqc.mjs rank zzz
no candidates match "zzz" — showing unfiltered list
SILVER-2 — Coverage threshold enforced — 2 files · small effort ⚠ ci-config
…
```

A Verdict with no `effort_tier` prints `unknown effort — recheck needed`. With no Verdicts yet, it prints nothing.

## `ids <arg>`

Turns a selector into the Rule IDs to audit, one line per Tier, so audits can run per Tier (in parallel if the agent can). `<arg>` is one of:

| Arg | Selects |
|---|---|
| `full` | Every Rule |
| `recheck` | Rules whose Verdict is `fail` or `partial`, or that have no Verdict (`na` is excluded) |
| a Tier ID, e.g. `SILVER` | Every Rule in that Tier |
| `ID,ID,...` | Exactly those IDs |

```
$ node .eqc/bin/eqc.mjs ids recheck
BRONZE: BRONZE-6
SILVER: SILVER-2,SILVER-3
GOLD: GOLD-1
$ node .eqc/bin/eqc.mjs ids BRONZE-6,GOLD-1
BRONZE: BRONZE-6
GOLD: GOLD-1
```

With no arg it prints `usage: eqc.mjs ids <recheck|full|TIERID|ID,ID,...>` and exits 1. Unknown IDs are grouped under `UNKNOWN`.

## `get <ID,ID...>`

Prints one line of JSON: an array with `{rule, compliance}` for each ID. `rule` comes from the Index, `compliance` from the latest Verdict. Either is `null` if not found (an unaudited Rule has `compliance: null`). IDs may be separated by commas or spaces. Auditors and fixers use it to start from prior evidence.

```
$ node .eqc/bin/eqc.mjs get SILVER-2,GOLD-9
[{"rule":{"id":"SILVER-2","tier":"SILVER","order":2,"title":"Coverage threshold enforced","detail":"CI enforces a minimum test coverage percentage, and the build fails when it drops below it.","detection_hint":"Look for evidence in repo config and CI files that: …","applies_to":["all"],"conflict_note":null,"source_line":26},"compliance":{"id":"SILVER-2","status":"fail","evidence":"No coverage threshold in jest.config.js or CI.","notes":"Add coverageThreshold and a CI step.","file_count":2,"effort_tier":"small","blast_radius":["ci-config"]}},{"rule":null,"compliance":null}]
```

## `merge <file>`

The only way Verdicts enter `compliance.json`. The file holds Verdicts from one Audit, as `{"results":[...]}` or a bare array (see the merge input below). The Engine:

1. validates every entry (known ID, status is `pass|partial|fail|na`); on any problem, prints each one and exits 1 without changing anything,
2. replaces existing Verdicts with the same ID and appends new ones,
3. drops `file_count`, `effort_tier` and `blast_radius` from `pass` and `na` entries,
4. recomputes the tier summary and the Compliance level, and stamps today's date,
5. writes `compliance.json`, updates `baseline.json` (see [`baseline.json`](#baselinejson)), and refreshes the report.

Merging is safe to repeat. After writing, `merge` prints the baseline, and a `guard` line when there are regressions.

```
$ node .eqc/bin/eqc.mjs merge .eqc/tmp/audit-1.json
merged 17 results · level: BRONZE
baseline: BRONZE · 13 protected
report: …/docs/eqc-report.md
```

Re-auditing `BRONZE-1` as `fail` (and `SILVER-2` as `pass`) produces the `HARD_FAIL` case. The baseline level stays `BRONZE`, and `guard` now has two regressions (`BRONZE-1`, and the level drop):

```
$ node .eqc/bin/eqc.mjs merge .eqc/tmp/audit-3.json
merged 2 results · level: HARD_FAIL
baseline: BRONZE · 14 protected
guard: 2 regressions — run eqc guard
report: …/docs/eqc-report.md
```

Validation errors:

```
$ node .eqc/bin/eqc.mjs merge .eqc/tmp/bad.json
merge: entry 0: unknown rule id "BRONZE-99"
merge: entry 0 (BRONZE-99): status must be one of pass|partial|fail|na, got "ok"
$ echo $?
1
```

An unreadable file prints `merge: cannot read <path>: <reason>` and exits 1.

## `reset`

Deletes `rules.json`, `compliance.json`, `doc-meta.md` and `baseline.json` (works on any OS; missing files are fine). Keeps `milestones.json`, `plans/`, `config.json` and `standard/`. Deleting the baseline forgets the protected Rules, so the next merge starts a new one. `eqc check <new-standard>` runs it before re-indexing.

```
$ node .eqc/bin/eqc.mjs reset
reset: removed rules.json, compliance.json, doc-meta.md, baseline.json (kept milestones, plans, config, standard)
$ node .eqc/bin/eqc.mjs report
No index yet — run `eqc check` in your AI agent first (it indexes the standard).
```

## `chunks <ID>`

Reads `.eqc/plans/<ID>.md` and prints progress. Chunk lines must look like `- [ ] 1 [mechanical] path/a, path/b`.

```
$ node .eqc/bin/eqc.mjs chunks SILVER-3
1/3 done · next: 2 [mechanical] src/ui/c.js, src/ui/d.js
$ node .eqc/bin/eqc.mjs chunks SILVER-3        # after ticking 2 and 3
all done (3/3)
$ node .eqc/bin/eqc.mjs chunks SILVER-9
no plan
```

Missing `<ID>` prints `usage: eqc.mjs chunks <ID>` and exits 1. "No plan" exits 0.

## `check-ids <doc>`

Validates the Index against the Standard file. See [writing-a-standard.md](writing-a-standard.md#how-check-ids-validates) for what it checks.

```
$ node .eqc/bin/eqc.mjs check-ids standards/example.md
check-ids: 17 rules OK
```

On a mismatch it prints `<ID>: <reason>` per problem and exits 1. A missing doc prints `check-ids: doc not found: <path>` and exits 1. It needs an Index, so it exits 2 without one.

## `milestone add '<json>'`

Appends a Milestone to `milestones.json` and prints its ID. Required fields: `rule_id`, `tier`, `status` (`done|partial|blocked|failed`), `summary`. Optional: `id` (default `M-<timestamp>`), `date` (default today).

```
$ node .eqc/bin/eqc.mjs milestone add '{"rule_id":"SILVER-2","tier":"SILVER","status":"done","summary":"Added coverageThreshold 80 and CI step"}'
milestone: M-1790678776834
```

```
$ node .eqc/bin/eqc.mjs milestone add '{"rule_id":"SILVER-2","status":"done"}'
milestone: missing required field(s): tier, summary
$ node .eqc/bin/eqc.mjs milestone add '{"rule_id":"SILVER-2","tier":"SILVER","status":"finished","summary":"x"}'
milestone: status must be one of done|partial|blocked|failed
```

Both errors exit 1.

## `config get <dotted.key>`

Prints a value from `.eqc/config.json`. Nested keys use dots (`gates.ci_config`). Objects and arrays print as JSON; other values as plain text. A missing key or missing file exits 1.

```
$ node .eqc/bin/eqc.mjs config get report_path
docs/eqc-report.md
$ node .eqc/bin/eqc.mjs config get nothing
config: no such key: nothing
$ echo $?
1
```

The Prompts read `standard.path`, `stack.tags`, `ci_paths`, `cheap_model` and the `gates.*` keys. The test fixture's `config.json` contains only `schema` and `report_path`, so those other keys must be present in a real project's config, or `config get` exits 1 for them.

## File shapes

### `rules.json` (the Index)

Written by the agent when indexing. Tiers are ordered lowest first.

```json
{
  "schema": 1,
  "standard": { "title": "Example Engineering Quality Standard", "version": "1.0", "date": "2026-01-15", "source_path": "standards/example.md" },
  "stack_tags": ["all"],
  "indexed_at": "2026-01-15",
  "tiers": [
    { "id": "BRONZE", "name": "Bronze", "order": 1, "section_heading": "Bronze" }
  ],
  "rules": [
    {
      "id": "BRONZE-1",
      "tier": "BRONZE",
      "order": 1,
      "title": "CI runs on every pull request",
      "detail": "A pipeline builds and tests each pull request automatically. …",
      "detection_hint": "Look for evidence in repo config and CI files that: …",
      "applies_to": ["all"],
      "conflict_note": null,
      "source_line": 14
    }
  ]
}
```

### `compliance.json`

Written only by `merge`. Never edit it by hand.

```json
{
  "schema": 1,
  "audited_at": "2026-09-29",
  "standard_version": "1.0",
  "results": [
    { "id": "BRONZE-1", "status": "pass", "evidence": ".github/workflows/ci.yml runs build and test on pull_request." },
    {
      "id": "BRONZE-6", "status": "partial",
      "evidence": "npm audit runs in CI but only warns.",
      "notes": "Set --audit-level=high so it fails the build.",
      "file_count": 1, "effort_tier": "trivial", "blast_radius": ["ci-config"]
    }
  ],
  "tier_summary": {
    "BRONZE": { "pass": 5, "fail": 0, "partial": 1, "na": 0, "total": 6 },
    "SILVER": { "pass": 4, "fail": 2, "partial": 0, "na": 0, "total": 6 },
    "GOLD":   { "pass": 4, "fail": 1, "partial": 0, "na": 0, "total": 5 }
  },
  "current_tier": "BRONZE"
}
```

`current_tier` is a Tier ID, `HARD_FAIL`, or `NONE` (lowest Tier not fully audited). A Tier counts as reached only if every Rule in it has a Verdict and none is `fail`. It is the Compliance level. `notes` and the effort fields appear only on `fail` and `partial` entries. `total` counts every Rule in the Tier, audited or not (including `na`).

### `baseline.json`

Written only by `merge`, never by hand. Each merge sets `protected` to the previous protected Rules plus every Rule that passes now, in Index order. `level` is the highest Compliance level reached so far and is kept when a later merge would lower it. `reset` deletes the file. Commit it: CI's `guard` reads it.

The only way to lower the baseline is to delete the file by hand. That is a deliberate decision to accept a lower bar, so review it like any other change.

```json
{
  "schema": 1,
  "standard_version": "1.0",
  "level": "BRONZE",
  "updated_at": "2026-09-29T10:14:02.512Z",
  "protected": ["BRONZE-1", "BRONZE-2", "BRONZE-3", "BRONZE-4", "BRONZE-5"]
}
```

The example lists only the Bronze Rules. A real file lists every Rule that has passed.

### `milestones.json`

A JSON array, appended to by `milestone add`.

```json
[
  {
    "id": "M-1790678776834",
    "date": "2026-09-29",
    "rule_id": "SILVER-2",
    "tier": "SILVER",
    "status": "done",
    "summary": "Added coverageThreshold 80 and CI step"
  }
]
```

### Merge input

What an Audit returns, written to a file (usually under `.eqc/tmp/`) and passed to `merge`. Either form is accepted:

```json
{"results":[
  {"id":"BRONZE-1","status":"pass","evidence":"..."},
  {"id":"SILVER-2","status":"fail","evidence":"...","notes":"...","file_count":2,"effort_tier":"small","blast_radius":["ci-config"]}
]}
```

or a bare array `[ {...}, {...} ]`.

| Field | Required | Values |
|---|---|---|
| `id` | yes | A Rule ID present in the Index |
| `status` | yes | `pass`, `partial`, `fail`, `na` (evidence must say why the Rule does not apply) |
| `evidence` | expected | At most 2 sentences plus file paths, or a command and its output |
| `notes` | for fail/partial | What is missing or what to do |
| `file_count` | for fail/partial | Number of distinct files to change |
| `effort_tier` | for fail/partial | `trivial`, `small`, `medium`, `large` |
| `blast_radius` | for fail/partial | Array of `ci-config`, `package-install`, `architecture`, `large-sweep` (may be empty) |

The Engine enforces only `id` and `status`. Leaving out `effort_tier` on a failing Rule is accepted but `rank` then reports `unknown effort — recheck needed`.
